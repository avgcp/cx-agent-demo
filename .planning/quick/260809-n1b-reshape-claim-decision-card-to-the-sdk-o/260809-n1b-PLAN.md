<the_contract>
This was established by disassembling the deployed SDK bundle
`https://www.gstatic.com/chat-messenger/sdk/prod/v1.16/chat-messenger.js`. It is read source, not
inference. Carry it forward.

The SDK builds an `order_summary` card from the payload `b` like this:

```
case "order_summary":
  c = new DF_Mzz(a.utterance.utteranceId, b.id);
  c.productItem   = b.productItem;
  c.costBreakdown = b.costBreakdown;
  c.paymentMethod = b.paymentMethod;
  c.actions       = b.actions;
```

and the render functions read exactly:

| Section | Sub-fields |
|---|---|
| `productItem` | `title`, `subtitle`, `price`, `imageUri` |
| `costBreakdown` | `subtotal`, `salesTax`, `discount`, `shipping`, `total` |
| `paymentMethod` | `brand`, `lastFour` |
| `actions` | `primaryLabel`, `secondaryLabel` |

Every money value goes through `Intl.NumberFormat` over a **google.type.Money** shape:
`{ units: <int>, nanos: <int>, currencyCode: <string> }`.

Known renderer behaviours:
- An **absent top-level section** renders an empty-state template — it does not error.
- `discount` and `shipping` are **suppressed when zero** (`units===0 && nanos===0`).
- `subtotal`, `salesTax` and `total` are rendered **unconditionally**.

**The payload IS the tool's declared `parameters`.** A widget tool returns
`{summary, widget_tool_status, payload}` and `payload` is shaped by whatever the tool declares. The
platform adds `"type": "order_summary"` itself — do **not** declare a `type` parameter.

**What the tool declares today** (the whole defect — matches none of the above):
```json
{ "issue_label": "screen replacement", "claim_ref": "CLM-24863", "deductible": 25,
  "claim_amount": 420, "auto_approval_cutoff": 750, "device": "Apple iPhone 16 Pro Max",
  "decision": "AUTO_APPROVE", "type": "order_summary" }
```
The SDK builds the card, finds all four sections undefined, and draws nothing usable — so the raw
payload is what the user sees. A schema mismatch in the tool's `parameters`. Not an SDK limitation
and not an agent defect.
</the_contract>

<the_mapping>
The mapping to implement. `resolve_claim` already computes every input; nothing new is invented.

| Card slot | Source (all already in `resolve_claim`) | Example |
|---|---|---|
| `productItem.title` | `device` | `Apple MacBook Pro 16"` |
| `productItem.subtitle` | `labels[issue]` (sentence-cased) + `·` + `ref` | `Keyboard replacement · CLM-24863` |
| `productItem.price` | Money(`amount`) | 420 |
| `costBreakdown.subtotal` | Money(`amount`) — repair cost before excess | 420 |
| `costBreakdown.discount` | Money(`excess`) — the excess deducted | 25 |
| `costBreakdown.total` | Money(`amount - excess`) — paid out | 395 |
| `actions.primaryLabel` | **the decision** — `AUTO_APPROVE` → `Approved on the spot`; `HUMAN_REVIEW` → `Passed to a specialist` | |
| `actions.secondaryLabel` | **the cutoff** — `On-the-spot limit $1,500` | |

`paymentMethod`, `imageUri`, `salesTax`, `shipping`: **omitted** (see contingencies).

**Where the two orphans went.** `decision` and `auto_approval_cutoff` have no native slot. They are
the demo's headline beat, so they are **not dropped** — they take the `actions` pair, which is where
the eye lands. Both also remain in `resolve_claim`'s return for the agent's spoken line and the
record; only their *card* home is new.

**Arithmetic rule (non-negotiable):** `subtotal`, `discount` and `total` are derived inside
`resolve_claim` in Python from `amount` and `excess`, which the tariff already produced. The model
supplies no figure. `total = max(amount - excess, 0)`.
</the_mapping>
