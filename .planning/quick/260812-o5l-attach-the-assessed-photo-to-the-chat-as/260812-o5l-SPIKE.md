# 260812-o5l — SPIKE: can a Python tool reach the uploaded photo?

## Verdict

**FEASIBLE**, by one mechanism and one only:

> **`context.user_content`** carries the uploaded image to a Python tool as
> `Part.inline_data` — a `Blob` whose `.data` is the **base64 of the image, ready to hand
> straight to Resend** — but **only on the turn the image was uploaded**. It is gone from
> every later turn. To use it on the packet turn it must be **captured on the upload turn and
> carried forward in session variables**, in slices of ≤ 262,144 bytes each.

Both halves were proven by running them, not by reading docs.

## How it was proven, without spending demo-app quota

Two tools that this project had not used before made the whole spike cheap and safe:

| Tool | What it bought |
|---|---|
| **`apps.executeTool`** (`POST {app}:executeTool`) | Executes a Python tool **directly, with no conversation**. Takes `args`, `variables` and a `context`. Every introspection result below cost **zero** conversation quota. |
| **`SessionInput.image`** on `runSession` | An image can be pushed into a conversation over the API exactly as the widget pushes it — the record shows the identical `chunks[].image` object. No browser needed to test the photo path. |

All five live conversations ran against a **throwaway app `o5lspikeprobe`**, created for the
spike and deleted afterwards. **No conversation was run against the chat or voice app, and no
existing resource on either was modified.** A probe tool was briefly created on the chat app
for introspection only (never attached to any agent) and deleted; the chat app is back at its
original 10 tools.

## What the tool runtime actually exposes

`type(context).__name__ == "ToolContext"`, from module `ces_internal` at
`/usr/bin/entry/ces_internal.py`. Its fields are exactly:

```
actions  agent_name  events  function_call_id  invocation_id
session_id  state  streaming_stage  user_content
```

plus the methods `parts()`, `get_last_user_input()`, `get_last_agent_output()` — all three
typed `-> list[ces_internal.Part]` — and `get_variable` / `set_variable` / `remove_variable`.

The data model, read out of the module's own source:

```python
class Blob(BaseModel):
  display_name, data: Optional[bytes], mime_type
  @property
  def raw_data(self) -> bytes: return base64.b64decode(self.data)

class Part(BaseModel):        # model_fields, exactly and only:
  function_call, function_response, inline_data, text
```

**`Blob.data` already holds base64** (the `raw_data` property is what decodes it). Resend wants
base64 in `attachments[].content`. So the bytes never have to be re-encoded — `blob.data.decode()`
is the attachment content, verbatim.

## The finding that decides the design: the image lives for exactly one turn

Conversation `o5lspike1`, three turns. Turn 0 carried the text *"Here is the photo of the
damage."* plus a real 1,148,051-byte PNG (1,530,736 base64 chars — the project's own
`evidence-laptop-photo.png`). The probe tool ran on every turn and reported what it could see:

| Turn | `context.user_content.parts` | `context.parts()` (full history) | `context.events` parts |
|---|---|---|---|
| **0** (image arrives) | `[text:32, **inline_data image/png: 1,530,736**]` | `[text:32, function_call]` | `text:32`, `fc` |
| 1 | `[text:20]` | `[text:32, fc, fr, text:2, text:20, fc]` | all text / fc / fr |
| 2 | `[text:15]` | 10 parts, all text / fc / fr | all text / fc / fr |

Read that table twice. **`user_content` on turn 0 is the only place the image bytes ever
appear.** By turn 1 the history retains turn 0's *text* and drops its image entirely — not
truncated, not a URI, absent. `get_last_user_input()` likewise returns only the current turn's
parts.

## What was ruled out, and how

| Candidate | Ruled out by | Verdict |
|---|---|---|
| **1. `ToolContext` exposes the attachment on a later turn** | The table above, run live | **NO** — history strips image parts |
| **1b. `ToolContext` exposes it on the upload turn** | The table above, run live | **YES** — this is the mechanism |
| **2. A GCS landing spot / URI handle** | `Part.model_fields` is exactly `{function_call, function_response, inline_data, text}` — **the CES `Part` model has no URI-bearing field at all** (no `file_data`, no `file_uri`). The API's own `Chunk` schema matches: an image is `image.data` + `image.mimeType`, inline, with no URI sibling. A probe that explicitly looked for `file_data`/`fileData` on every part of every event found none, ever. | **NO** — there is no URI to reach, so there is nothing for a `gcs-upload` config to hand a tool. Consistent with 260809-nt7's finding that widget upload needs no bucket at all. |
| **3. Self-referential `conversations.get` from inside the tool** | The sandbox has **no `google.auth`, no `requests`, no `google.cloud.storage`** (all `ModuleNotFoundError`) and **12 environment variables**, none of them a credential: `BORG_CONTAINER_RUNTIME, GPG_KEY, LANG, MPLCONFIGDIR, PATH, PYTHONPATH, PYTHON_GET_PIP_SHA256, PYTHON_GET_PIP_URL, PYTHON_PIP_VERSION, PYTHON_VERSION, SANDBOX_INPUT_OUTPUT_DIRECTORY, XBOX_PARALLEL_SOCKET`. There is no way to mint a bearer token. | **NO** — dead before the circularity question even arises |
| **4. Pass base64 through a tool parameter** | Excluded by the brief; also the model would have to reproduce 1.5 M characters | **NO** |

## Carrying it forward: session variables, proven to 5 MB

Since the bytes must survive from the upload turn to the packet turn, the spike tested whether
the session variable store can hold them.

**There is a hard per-variable ceiling, and hitting it kills the whole turn.** Writing the full
1.5 MB base64 to one variable returned, from `runSession` itself — not from the tool:

```
HTTP 400  FAILED_PRECONDITION
Variable update for key 'o5l_photo_b64' is too large: 1530738 bytes (max: 262144)
```

That is not a `{"sent": false}`-style soft failure. **The customer's turn fails.** Any
implementation must therefore slice *before* writing, and cap the total — the size guard is
mandatory, not a nicety.

Sliced, it works, and it survives the turn boundary intact:

| Conversation | Written on the upload turn | Read back on the next turn |
|---|---|---|
| `o5lchunk2` | 31 vars × 50,000 chars = **1,530,736** | 31 keys, **1,530,736** — exact |
| `o5lchunk3` | 7 vars × 250,000 chars = **1,530,736** | 7 keys, **1,530,736** — exact |
| `o5lbulk1` | 20 vars × 250,000 chars = **5,000,000** | 20 keys, **5,000,000** — exact |

**Cost of carrying it: none on later turns.** The turn that writes the variables echoes them
back in its own `updatedVariables` chunk, so that response is as large as the payload (5.0 MB
for the bulk test). Every *subsequent* turn is unaffected: the read-back turn's whole
`runSession` response was **2,744 bytes** and took **1.8 s**. The base64 is not replayed into
the model's context, not echoed in later diagnostics, and costs no measurable latency.

## The mechanism, stated as the build should implement it

1. **On the upload turn**, inside the tool that already runs there (`assess_screen_crack`), walk
   `context.user_content.parts`, take the last part whose `inline_data.mime_type` starts with
   `image/`, and read `inline_data.data` — that is the base64 string.
2. **Guard**: if it is absent, or longer than the cap, write nothing and carry on. Writing an
   oversize value fails the customer's turn.
3. **Slice** into ≤ 250,000-char pieces, write each to its own session variable, plus a count
   and the mime type.
4. **On the packet turn**, `send_case_record_email` reassembles the pieces in order and passes
   the result as Resend `attachments: [{filename, content}]`.
5. Every step wrapped so that a failure degrades to *packet without photo*, never to *no packet*.

## Two platform traps found on the way, both worth carrying forward

1. **Tool code changes do not take effect immediately.** A conversation started seconds after a
   `tools.patch` executed the **previous** version of the code; the same tool, called ~40 s
   later in the same conversation, ran the new one. The patch response and a byte-for-byte
   read-back both said the new code was live — **read-back does not prove the runtime picked it
   up.** This burned one conversation here and would read as a mysterious no-op in any future
   task. **Wait ~25 s after patching a tool before invoking it.**
2. **App creation is an LRO**, and `gemini-2.5-flash` is **not available in `us`** (only
   `gemini-3.1-flash-live` was accepted). Both only matter for throwaway apps, but both cost a
   round trip to discover.
