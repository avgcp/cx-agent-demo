## 1. The generator — it was never random

`resolve_claim` mints the reference, on both apps, in the same nine lines. **`resolve_claim` was
never read, echoed, printed or persisted.** Everything below was obtained with boolean/shape probes
that emit only presence flags, digit-only regex captures, and an identifier-whitelisted line
sanitiser that masks every string literal — the tool carries the live Resend key on the line above.

The probe returned, on **both** apps:

```
contains random  : False (n=0)      contains randint : False (n=0)
contains uuid    : False (n=0)      contains secrets : False (n=0)
contains hashlib : False (n=0)      contains time.time : True (n=1)
string literal   : 'CLM-{24000 + offset + seq}'
string literal   : 'CLM-24xxx'
sanitised lines  : seq = int(<id>.<id>.<id>(<STR>, 0)) + 1
                   offset = int(time.time()) % 900
```

So the generator is, verbatim:

```
seq    = <session counter "claim_seq"> + 1
offset = int(time.time()) % 900          # inside a try, 0 on failure
ref    = f"CLM-{24000 + offset + seq}"
```

**It is not a small random range. It is a deterministic 900-second wheel.** The reference space is
900 values wide and it *repeats every fifteen minutes*. Two claims resolved at the same
second-modulo-900, with the same session sequence number, get the **identical** reference —
guaranteed, not by chance.

### Proven against the store, 22/22

Every generated reference in the store was checked against `ref − 24000 − seq == t_resolve % 900`.
`created_at` is written later by `record_claim`, so the residual is the lag between the two tool
calls. **All 22 land in a 1–5 second band. Not one outlier.**

| `created_at` | ref | `num−24000` | `epoch%900` | lag (s) |
|---|---|---|---|---|
| 2026-08-13T12:25:04Z | CLM-24599 | 599 | 604 | 5 |
| 2026-08-13T17:38:58Z | CLM-24536 | 536 | 538 | 2 |
| 2026-08-14T01:45:42Z | CLM-24040 | 40 | 42 | 2 |
| 2026-08-14T03:11:31Z | CLM-24690 | 690 | 691 | 1 |
| **2026-08-14T10:40:00Z** | **CLM-24599** | **599** | **600** | **1** |

The last two rows *are* the collision. The 2026-08-13 MacBook claim resolved at `t%900 = 598`; the
2026-08-14 Dell claim resolved at `t%900 = 598`. Twenty-two hours and fifteen minutes apart — an
exact multiple of the wheel. Birthday probability over 900 slots with 22 draws is ≈ 23%; exactly one
collision is precisely what the model predicts.

## 3. The fix I chose, and why

**Two changes, applied to both apps. The generator was widened *and* the writer was given a hard
refusal.** The brief is right that the defence is worth having regardless: it converts a silent
overwrite into a visible, typed failure, and it protects against a generator I do not control
changing under me.

### 3a. Widen the wheel — `resolve_claim`, both apps

Three edits, all **digit- and letter-only**, all anchored on literals already known from the shape
probe, all asserted to occur **exactly once** before replacement:

```
int(time.time()) % 900        ->  int(time.time()) % 10000000
CLM-{24000 + offset + seq}    ->  CLM-{24000000 + offset + seq}
CLM-24xxx                     ->  CLM-NNNNNNNN          (a stale format comment)
```

**Delta: +11 characters on each app.** No identifier added, no control flow touched, no new `def`,
no line moved.

| | before | after |
|---|---|---|
| reference space | **900** | **10,000,000** |
| repeat period | **15 minutes** | **115.7 days** |
| format | `CLM-24599` (5 digits, variable) | `CLM-30705868` (**always 8 digits**) |
| range | 24001–24900 | 24,000,001–34,000,000 |

**Why this shape and not the alternatives.**

- *Why not keep a narrow space and rely only on the `record_claim` refusal?* Because a refusal is a
  degraded claim — the customer is told a reference, then the store declines it. The generator has
  to stop producing duplicates in the first place; the refusal is the backstop.
- *Why a modulus at all rather than the raw epoch?* `CLM-1786704802` is ten digits. A demo reads
  this number onto a card, into an email subject and, on voice, into a spoken sentence. 115.7 days
  of guaranteed uniqueness is far longer than the demo programme, and it buys a reference a human
  can read.
- *Why not derive it from the policy?* That would make *cross-policy* collision structurally
  impossible but leave *same-policy* collision — which silently destroys a claim just as badly —
  entirely unaddressed. It also fixes only the symptom this audit happened to surface.
- *Why fixed width?* `24000 + offset` with a wide modulus produces `CLM-24001` and `CLM-10023999`
  from the same generator. A reference whose length varies is a reference that breaks templates,
  spoken normalisation and eyeballs. Basing at 24,000,000 pins it at 8 digits for the whole cycle
  and keeps visual continuity with the existing `CLM-24…` corpus.

Two consecutive live invocations one second apart returned `CLM-30705244` and `CLM-30705245` — the
wheel advancing at one per second, exactly as designed. Seeding `claim_seq = 7` instead of `0`
raised the reference by 11 over the same base, proving the session counter is still live.

### 3b. Refuse a cross-policy overwrite — `record_claim`, both apps

A **1,718-character block** inserted immediately before the existing policy-object `GET`, anchored
on that step's own comment line (asserted unique). It performs one extra `GET` of
`claims/by-ref/{CLAIM_KEY}.json` **before any write**:

| observed | behaviour |
|---|---|
| **404** | new reference — proceed normally |
| **200**, same policy | a legitimate re-write of the same claim — falls through to `duplicate_replaced` |
| **200**, **different policy** | **REFUSE.** `recorded: false`, `ref_collision: true`, `status_code: 409`, `error_stage: "collision"`, and **neither PUT is issued** |
| anything else | abort with `error_stage: "precheck"` — never write blind |

It follows the tool's existing discipline exactly: the status is read as
`int(getattr(r, "status_code", 0) or 0)` and **never** from `.ok`; every new field starts
false/0 and is only assigned from an observed status; an exception is caught, typed and returned
with `recorded` still false.

**Two new return fields: `precheck_status` and `ref_collision`. `store_calls` is now 4 on a full
write, not 3** (1 pre-check GET + 1 read GET + 2 PUTs). The store contract is updated.

**Proven by invocation on both apps, 17/17 each,** on a throwaway policy and then again against the
real colliding key:

```
A  new ref, policy A     recorded:true  precheck_status:404  ref_collision:false store_calls:4
B  same ref, same policy recorded:true  precheck_status:200  duplicate_replaced:true, count unchanged
C  same ref, OTHER policy recorded:FALSE ref_collision:TRUE  status_code:409 store_calls:1
                         by_policy_status:0  by_ref_status:0
                         error: "claim_ref CLM90000003 already belongs to policy PDP100999
                                 - refusing to overwrite it"
```

And against live demo data, on both apps:

```
record_claim(claim_ref="CLM-24599", policy_id="PDP-100294", ...)
  -> recorded:false  ref_collision:true  status_code:409
     "claim_ref CLM24599 already belongs to policy PDP100017 - refusing to overwrite it"
```

**Yes — `record_claim` now refuses a cross-policy overwrite, on chat and on voice.**

## 4. The repair — stated, not silent

`by-ref/CLM24599.json` described the Dell XPS 14 on `PDP100017` (Alex Chen, `2026-08-14T10:40:00Z`,
$560). `by-policy/PDP100294` still listed `CLM-24599` as an Apple MacBook Pro 16" (Jordan Rivera,
`2026-08-13T12:25:04Z`, $840).

**Two claims were issued one reference. One of them has to lose it. That is the unavoidable
consequence of the collision and there is no repair that avoids it** — so the question is only
*which*, and on what stated grounds.

**Decision: the Dell claim on `PDP100017` keeps `CLM-24599`. The MacBook claim on `PDP100294` was
re-issued as `CLM-30623899`.** Three reasons, in order of weight:

1. **`CLM-24599` on `PDP100017` is named as live demo data.** Breaking it is not an option.
2. **It is the claim `by-ref` already, correctly, describes.** Keeping it means the authoritative
   object does not move at all — the smaller change.
3. **The MacBook claim is one of 25 test claims on `PDP100294`** from 06-03's live chat runs, and it
   is *not* the demo claim; `CLM-24690` is. `CLM-30623899` is the newest-but-one entry in an array
   nobody reads by reference.

I chose **re-issue over deletion**. Deleting destroys a record a real conversation produced; the
claim itself is not at fault, only its reference. And I chose re-issue over *making `CLM-24599`
unresolvable*, because that would sacrifice a live demo claim to protect a test one.

**The loss is recorded in the store rather than hidden.** The re-issued record carries two extra
fields so anyone auditing it later sees exactly what happened:

```json
"claim_ref":      "CLM-30623899",
"superseded_ref": "CLM-24599",
"repair_note":    "reference re-issued 2026-08-14 (quick task 260814-80f): CLM-24599 was minted
                   twice by the 900 s generator wheel and CLM-24599 now belongs solely to the
                   Dell XPS 14 claim on PDP100017"
```

The new reference was **minted by the new scheme from that claim's own resolve time**
(`created_at` 2026-08-13T12:25:04Z less the measured 6 s `record_claim` lag), so it is reproducible
rather than arbitrary. A matching `by-ref/CLM30623899.json` was written; `by-ref/CLM24599.json` was
**not touched**.

Serialisation is `json.dumps(obj, sort_keys=True, separators=(",", ":"))` — 06-01's load-bearing
choice, preserved. Written with the executor's own credentials via `gcloud storage`; no HMAC key was
read, minted or handled.
