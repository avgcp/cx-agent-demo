## What is wrong today — two established causes

1. **`claim_decision_card` has `textResponseConfig: {type: NONE}`.** Per the CES discovery
   document, `WidgetToolTextResponseConfig.type` values mean:

   | Value | Actual meaning |
   |---|---|
   | `NONE` | **"The LLM dynamically decides whether to generate a text response alongside the widget."** — NOT "no text" |
   | `LLM_GENERATED` | "The LLM is explicitly required to generate a text response." |
   | `STATIC` | A fixed `staticText` is always used. |

   With `NONE` the model routes its sentence into the widget's `summary` parameter (which
   renders nowhere) and stays silent. Observed silent on 2026-08-09; observed speaking a
   *paraphrase* ("I've looked into that, and I can approve this claim right now") on
   2026-08-10. So the beat is **non-deterministic**, not reliably broken — a presenter still
   cannot depend on it, and the paraphrase carries no figures.

2. **`claim_intake`'s instruction is self-contradictory.** One block says read the
   `explanation` **WORD FOR WORD**; another says do **not** repeat the figures and say only
   the short human part. That contradiction must be **resolved**, not papered over. Per the
   locked decision, **verbatim wins**.

`textResponseInstruction` is a **real field**, confirmed in the CES v1beta discovery
document: `WidgetToolTextResponseConfig { type, textResponseInstruction, staticText }`,
where `textResponseInstruction` is *"Instruction for the LLM on how to generate the text
response. Used as the description for the text response parameter if type is
LLM_GENERATED."*

**Mechanism note, confirmed on the live API by `260810-ifr`:** setting `LLM_GENERATED` adds
a **required `textResponse` string parameter** to the tool's input schema, whose description
is the `textResponseInstruction` verbatim. That is the enforcement — the model cannot call
the tool without composing that string. This will make `retrieveToolSchema` show a parameter
you did not declare. **That is expected and is not a violation of "do not change the card's
parameters"** — our declared `parameters` block stays byte-identical; the platform injects
`textResponse` on top of it.

## THE TRAP — the sentence gets emitted TWICE

`260810-ifr` set `LLM_GENERATED` on `cover_offer_actions` and the offer sentence appeared
**twice in the conversation record**:

| Message | Source |
|---|---|
| `msg1` — text + `toolCall` | the model's own output message |
| `msg3` — text + `payload` | the delivered widget message, sourced from the required `textResponse` parameter |

The decision-card turn on `NONE` emits only one text chunk and the delivered widget message
carries none. So the doubling is a direct consequence of `LLM_GENERATED` **combined with an
instruction that also tells the agent to say the thing aloud as its own message**. Both
produced the same sentence.

**`260810-ifr` wrote down the fix and this plan applies it up front rather than
rediscovering it:**

> *"drop the 'say the offer out loud as your own message' clause and let the widget's
> `textResponse` be the sole source. Because `LLM_GENERATED` makes that parameter
> **required**, the question cannot go missing."*

**Therefore the instruction rewrite in Task 2 must forbid the agent from sending any message
of its own in the card turn.** The card's `textResponse` is the single source. This is the
whole duplication-prevention design; do not soften it.

Whether the browser renders the duplicate once or twice is not determinable from a
server-side log. **Doubling the decision explanation on stage would be a worse defect than
the silence it replaces**, so this plan also makes the deployment repoint *conditional* on
the duplication check (Task 3).

## Mechanism choice — deterministic string first, verbatim transcription as the floor

`STATIC` is rejected: `staticText` is fixed and cannot carry per-claim figures ($840 screen,
$420 keyboard, $3,000 total loss, the `photo_blocked` no-figure branch).

`resolve_claim` already computes a customer-facing explanation string — `claim_intake`'s
existing instruction says to read *the `explanation`* word for word, and ROADMAP criterion 5
calls it "the verbatim-read decision explanation". The card's `productItem` is already
proven byte-identical to `resolve_claim`'s `card_product_item` via a `FIELD_MAPPING`
`dataMapping`, so **the same mechanism may be able to fill `textResponse` with zero model
involvement.** That is untested. Task 1 attempts it and falls back cleanly.

**The acceptance test is mechanism-agnostic and is the thing that actually matters:** in the
same conversation record, the emitted `textResponse` must be **byte-identical to
`resolve_claim`'s `explanation`**. If the mapping works, that is guaranteed. If the model
transcribes, it must be proven. Either way the string on screen is the tool's, not the
model's.
