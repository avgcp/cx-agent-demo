# 260806-u21 — Remove the wrong-subject photo guard from the chat app

The device-identity check is gone from `assess_screen_crack` in `Meridian Claim - Chat
(hardened)`, cut as **chat v6 `56a8b22a-2baf-4b18-9540-cdc6185acbee`**, and the live chat
deployment `d7bfbb93` now serves it. Five project documents that described the guard as
working now state the limitation instead.

> **Photo assessment confirms whether the reported damage is visible. It cannot verify that
> the photographed device is the insured device. Demos must use matching device/policy pairs.**

## The decision

User decision, 2026-08-06: **option 2 from 05-02-SUMMARY.md — accept the limitation.** Option 1
(agent-as-tool vision isolation) was explicitly not attempted. Rationale, in the user's
framing: *a guard that does not work is worse than none, because it reads as protection in
both the code and the runbook.*

Deploy scope was answered before execution: **push and repoint** (`a-push-and-repoint`), with
**offline verification only** — no live conversation test, because this session had no photo
of an undamaged device.

## What was removed

From `assess_screen_crack`:

- The `keyboard_visible` and `hinged_lid` parameters and their enum validation. Signature is
  now `assess_screen_crack(crack_visible, what_you_see)`.
- The device-inference block: laptop/phone signal counting, keyword matching, `inferred`, and
  the `photo_device_seen` state write.
- The `WRONG_SUBJECT` return and everything that read `device_category`.
- The `inferred == "unclear"` disjunct — the unclear branch now rests on `crack_visible` alone.

Elsewhere:

- `app.json` — the `photo_device_seen` variable declaration. (`importApp` does **not** drop a
  removed variable declaration; it had to be cleared with an explicit `apps.patch` on
  `variableDeclarations`. Verified absent afterwards: 37 variables remain.)
- `agents/claim_intake/instruction.txt` — the paragraph telling the agent to answer the
  physical questions from the picture alone and ignore what the policy covers, replaced with:
  *"Describe the object and the damage plainly in `what_you_see`, exactly as they appear in
  the picture."* The four outcome bullets are unchanged. A sweep of the whole instruction set
  found no other sentence implying the photo is checked against the policy device.
- `resolve_claim` — logic unchanged; one comment added noting that `"rejected"` is no longer
  produced and is retained defensively in `photo_blocked`.

## What was strengthened

The `crack_visible="unclear"` option text is now the only thing between a junk photo and an
approval, so it explicitly names *"there is no screen and no device visible in the picture at
all"* as one of its cases, plus: *"If what you are looking at is not a device with a screen you
can assess, the answer is `unclear` — never `yes`."* The docstring was mirrored into
`assess_screen_crack.json`'s `pythonFunction.description` programmatically, so the two cannot
drift.

A comment at the top of the function records **why** the identity check is absent — both failed
versions, the root cause, and the fact that damage reporting is unaffected — so a future reader
does not "fix" the omission by reintroducing the same failure.

## Deviations

**[Rule 3 — blocking] The GCP project ID in the plan and brief is wrong.** Both say
`gemini-enterprise-trial-497817`. The app lives in **`insurance-agent-demo-500614`** (project
number 848218147479), confirmed by probing both: the trial project returns 403 *"CES API has
not been used in project…"*, while `insurance-agent-demo-500614` returns the app with
`displayName: "Meridian Claim - Chat (hardened)"`. All prior-session artifacts also use
`insurance-agent-demo-500614`. Worth correcting in whichever brief template carries it.

**[Rule 3 — blocking] `importApp` does not remove a deleted variable declaration.** After the
push, `photo_device_seen` was still declared on the app even though it was absent from the
imported `app.json` (`REPLACE` merges app-level fields rather than replacing the list). Cleared
with `PATCH apps/{app}?updateMask=variableDeclarations`. Anyone relying on `importApp` alone to
drop a session variable will silently leave it behind.

**[Rule 2 — missing correctness] `05-01-SUMMARY.md` also claimed the guard worked.** It was not
in the plan's file list, but its "Verified" section asserted *"Wrong subject → rejected, names
the covered device"*, which directly violates the must-have *"No project document tells a
reader that a wrong-object photo is rejected."* Corrected in place with a strikethrough plus an
explanation, preserving the record.

**Shell note (no impact on output):** the execution shell is zsh, where `$VAR:e` is parsed as a
history modifier — `"$APP:exportApp"` silently produced `/apps/xportApp` and a 404. All request
URLs use `${VAR}` bracing.
