## `capture_claim_photo` — what it does and where it fires

A **new, capture-only, vision-free tool** on the chat app, attached to `claim_intake`. It walks
`context.user_content.parts`, takes the last part whose `inline_data.mime_type` starts with
`image/`, reads `inline_data.data` (**already base64** — handed to Resend verbatim, never
re-encoded), refuses outright above 4,000,000 chars **writing nothing**, and otherwise slices at
250,000 chars into `photo_b64_0..N` plus `photo_b64_parts` / `photo_b64_mime` / `photo_b64_len` —
the exact variable names `send_case_record_email` already reassembles, so the mailer needed no
change to attach what this writes. It also sets `photo_capture_status = "received"`.

**It fires in the same turn the image arrives, on every claim that is not a cracked screen.**
Observed live on the liquid-damage run (`p23-bat-esc-j1`, turn 2): `capture_claim_photo` →
`{"captured": true, "photo_b64_len": 1530736, "parts": 7}`, and the only thing the agent said about
it was *"Thanks, I've got that on the file."*

**It returns nothing that describes the image** — `{captured, photo_b64_len, parts}` and no more.
That is the whole point. On a total-loss claim the device is inert; asking a vision model to report
damage it cannot see invites exactly the contamination this project already proved **unfixable by
prompting** (commit 2c22582, where the model reported "a black phone" for an unmistakable MacBook
because it already knew what the policy covered). There is nothing in the result for the model to
read back, so there is nothing to conform to.

`assess_screen_crack` is **byte-unchanged** (whole-object sha256 identical to the plan-start
capture). Its capture block was reused by contract, not by edit.

## The refusal is deterministic, not a request

`claim_intake`'s `beforeToolCallbacks[0]` gained a gate (+1,516 chars, a **pure insertion** —
`changed_span_old = 0`) that refuses `assess_screen_crack` with
`PHOTO_NOT_ASSESSED_FOR_THIS_ISSUE` unless the claim's damaged part is a cracked screen:

```
_screen_claim = (dx_issue == "screen") or
                (issue_category == "physical_damage" and not dx_issue and "q1=screen" in dx_answers)
```

Two notes on that predicate, both load-bearing. `issue_category` alone **cannot** discriminate — a
cracked screen and a broken keyboard are both `physical_damage` — so the plan's stated key had to be
widened to `dx_issue` with a pre-terminal fallback on `dx_answers`. And gating on a terminal
variable is only safe **because capture now lives in a separate, ungated tool**: a
`beforeToolCallback` that returns a dict short-circuits the tool before its body runs, which is
exactly why `assess_screen_crack` could never capture a photo volunteered mid-diagnostic (260812-o5l,
reproduced three times).

**Proven live: zero `assess_screen_crack` invocations on the liquid-damage claim** — not refused-
then-retried, never called at all, because the instruction routes the non-screen branch to
`capture_claim_photo` and the gate stands behind it as the deterministic backstop.

## What happens when the customer has no photo

**Nothing changes for them, and the record says so.** One ask, and if they decline, say there is
nothing to see, or simply answer the next question, the agent moves straight on. No second ask, no
"are you sure", no gate on the diagnostic, the decision, the price, the card or the customer email.

Proven end to end on a keyboard claim with no photo (`p23-t1appr-b1`): tariff $420 / $25 / cutoff

predated the `record_kind` split). Re-confirmed by direct invocation of the shipped mailer:
`record_kind="RECORD"` with no photo variables → `sent: true, status_code: 200, attached: false`.

## Platform finding: a CES tool cannot read a response header. At all.

Position P3 required the mailer to return `x-resend-daily-quota`. **It cannot be done.** Probed on
a throwaway app: `ces_requests` returns an `ExternalResponse` whose entire public surface is

```
json  ok  raise_for_status  reason  status_code  text
```

There is **no `headers` member of any kind**. So Resend's quota headers — and every other response
header — are unreachable from inside a CES Python tool. The first implementation scraped for them
and silently returned `""`, which is the same silent-success shape this project already had to fix
in `resolve_claim`, so it was replaced with an explicit
`"resend_daily_quota": "unavailable: CES ExternalResponse exposes no headers"`. **A caller can now
tell "quota fine" from "quota unknown".** Count sends, or read the figure in the Resend dashboard.

This task spent **21 Resend sends** (16 across 11 conversations, 5 via `executeTool`) against a
100/day free tier. Per-claim cost is now exactly 2 — one customer email, one record — up from ~1.15.
A 20-claim demo day is 40 sends, comfortably clear.

Two more `executeTool` findings that cost nothing and unlock a lot:

- **`variables` and `context` are a `oneof`** on `apps.executeTool` (`tool_execution_context`) —
  sending both returns 400. You get session state **or** a synthetic `ToolCallContext`, never both.
- The context shape that actually populates `context.user_content` is **mixed-case and undocumented**:
  `{"user_content": {"parts": [{"inlineData": {"mimeType": "image/png", "data": "<b64>"}}]}}` —
  outer key snake, inner key camel. `userContent` is silently ignored; `inline_data` is silently
  ignored; `mime_type` inside the blob is silently ignored. Every wrong spelling returns a
  well-formed 200 with an empty `Part`, so **a wrong guess looks exactly like a tool that found no
  image**. This is how the whole photo path was proven without a browser and without a conversation.
- **`generate_case_summary` cannot be tested by `executeTool`.** It is an `agentTool`, and the
  `{decision}` template does not resolve from the request's `variables` — both branches return
  `NO_PACKET_REQUIRED`. That is a false negative, not a result. Agent-as-tool needs a conversation.

## The thing that could not have been found by reading: this turn oscillates

The HUMAN_REVIEW email-confirmation turn broke **three different ways** while widening the Case
record step to both branches, and each failure was a different failure. This is 260812-o5l's
"recency trap" reproducing exactly, on a step o5l never touched.

| Arrangement of the Case record step | Approve path | Escalated path |
|---|---|---|
| **A** — trigger widened + a new "does not close the call" paragraph in the first block | cross-sell fires, no `end_session` | **completely SILENT turn** — packet filed, escalated, closed, not one word spoken (`d1`) |
| **B** — A, plus the speak-first rule merged into the step's last paragraph | untested | **whole step skipped** — a quoted farewell (`'"Thanks, Jordan - have a good day."'`, copied with the instruction's own quote marks) then `end_session`; no email, no packet, no escalation (`e1`) |
| **C** — v15 action body restored byte-exactly, only the trigger widened + `record_kind` named | **`end_session` on the record turn, cross-sell DEAD** (`g1`) | correct (`f1`) |
| **D — SHIPPED** — C plus one in-place sentence making the step branch-neutral | correct (`h1`) | correct (`j1`) |

The diagnosis, and the transferable part: **on v15 the Case record step did not run on the approve
path at all**, so the last thing the model read about that turn was the "Ask for photos by email"
step, whose final paragraph carries the AUTO_APPROVE `end_session` prohibition. Making the step run
on both branches inserted an *escalation-flavoured* block ("File the case record **for the
specialist**") after that prohibition, and the approve path started closing the call. The fix was
not to add a rule — every attempt to add prose degraded the other branch — but to make the existing
sentence **branch-neutral**: `File the case record. … it does not change how this turn ends: on
HUMAN_REVIEW the call still closes here, and on AUTO_APPROVE it still does not.` One sentence,
replaced in place, no new paragraph, the step's ending untouched. +301 chars.

**Carry forward: when you make an existing step run on a new branch, the risk is not the trigger —
it is that the step's prose was written for the old branch and now pulls the new one toward the old
branch's ending.** Neutralise the wording; do not append a correcting rule.

Two independent deterministic backstops make this survivable rather than fragile: if the model
captures instead of assessing on a screen claim, `resolve_claim` is refused with `PHOTO_REQUIRED`;
if it assesses on a non-screen claim, the callback refuses with `PHOTO_NOT_ASSESSED_FOR_THIS_ISSUE`.

## Deviations from plan

**[Rule 3 — blocking issue] `case_summary` was edited, against `untouched_by_contract`.**
The plan lists `case_summary` as byte-identical. It cannot be. Its first taskflow step is a hard
guard — *"If {decision} is anything other than `HUMAN_REVIEW` … respond with the single token
NO_PACKET_REQUIRED and nothing else. Stop there."* — and its `<role>`, `<primary_goal>`,
`<identity>` and constraint 6 all say the packet exists for human review. **Observed live before any
fix**: on the AUTO_APPROVE run `p23-t1appr-a1` the agent called `generate_case_summary` in exactly
the right place on exactly the right turn, and got back `NO_PACKET_REQUIRED`, so
`send_case_record_email` never ran. The plan's whole Task 1 was structurally impossible without this.

The edit is minimal and preserves the escalated packet exactly: the guard, the two step triggers,
the role/persona/identity and constraint 6 were widened to `HUMAN_REVIEW or AUTO_APPROVE`, and the
**only** substantive addition is one clause on the ACTION section saying that on an approved claim
no assessor action is required. All six headings, their order, the money-formatting rule and every
other section are untouched. 5,970 → 6,977 (+1,007) across two anchored batches. Widening the guard
alone was **not sufficient** — the role and persona kept winning and it still returned
`NO_PACKET_REQUIRED`, which is itself worth recording.

**[Rule 1 — bug] The `assess_screen_crack` gate is keyed on `dx_issue`, not `issue_category`.**

keyboard — both are `physical_damage` — so as written the gate would have let vision run on
non-screen `physical_damage` claims and refused nothing useful. Widened as described above. The

**[Rule 1 — bug] The quota field reports its own unavailability.** P3 asked for
