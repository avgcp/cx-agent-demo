<objective>
Settle the phase's one genuine unknown before any design depends on it: **what can a CES Python
code tool authenticate to?** One data point exists and only one — `resolve_claim` calls Resend
over HTTPS with an API key held in its own source, so **outbound HTTPS with a shared secret is
proven**. Everything else is assumption.

This plan answers the question by running code inside the platform, on a **disposable app**, so
that no live agent is at risk while the answer is unknown. It then picks the store, writes down
the claim record schema, and takes the user's lock on both.

Purpose: every later plan in Phase 6 hardcodes the mechanism this plan proves. Guessing it and
discovering the guess was wrong three plans later would cost two version cuts and a repoint.
Output: `06-01-SPIKE-FINDINGS.md` with five literal, greppable section headings.
</objective>

<operational_rules>
Carry all of these. They are not advice; each one has already cost this project a session.

1. **Bound every network call.** `curl --max-time 120 --connect-timeout 15`. No unbounded call.
2. **Take a fresh `gcloud auth print-access-token` immediately before each conversation.** An
   expired token has stalled executors by hanging on an interactive reauth prompt.
3. **Write artifacts incrementally — one section per tool call.** Do not compose a long document
   in a single tool-call argument; two executor sessions have died from an API transport error
   doing exactly that.
4. **Never read, echo, print or persist the source of `resolve_claim`** on either app. It holds a
   live Resend key. This plan has no reason to touch it at all.
5. **No `importApp`, ever.** It silently deletes server-only tools, and every on-disk export in
   this repo is STALE. All CES writes are direct `apps.*.create` / `apps.*.patch` with
   read-verify-patch-verify.
6. **Never plan or run a retry loop against CES.** Quota is ~1,000 input tokens/min against a
   120–150k-token conversation. Budget conversations explicitly; a 429 is a stop, not a retry.
7. **No package-manager installs.** CES Python tools use only the platform-provided
   `ces_requests` and the standard library. If the spike concludes a third-party dependency is
   required anywhere, that is a **blocking checkpoint**, not an install — no package legitimacy
   audit exists for this phase.
8. **A client-level write gate.** Before any non-GET call, assert the URL contains the app id you
   intend and does **not** contain `9ae7a0c3`. Log every refused call.
</operational_rules>

    `probe_sandbox` takes no meaningful input and returns one JSON object. It must **catch every
    exception per probe individually** and record the exception class and message as the probe's
    result — never let one failing probe abort the others, and never let the tool raise. Per 05-07,
    a swallowed exception is invisible, so every probe records its outcome explicitly rather than
    being inferred from absence.

    Probes, each recorded as a named key:

    A. **Imports.** Attempt, one at a time: `json`, `os`, `base64`, `hmac`, `hashlib`, `datetime`,
       `urllib.request`, `uuid`, `google.auth`, `google.auth.transport.requests`,
       `google.cloud.storage`, `google.cloud.firestore`. Record importable true/false per module.
    B. **Environment.** Record the *names* only of environment variables (never values) and whether
       any of `GOOGLE_CLOUD_PROJECT`, `GOOGLE_APPLICATION_CREDENTIALS`, `GCP_PROJECT`,
       `K_SERVICE`, `GAE_*` are present. Names only — an env dump could carry a secret.
    C. **ToolContext / session state.** Accept an optional `context` argument as the platform's
       documented `context`/`ToolContext` object and record: whether it arrives non-None, the sorted
       list of its public attribute names, and whether anything resembling session state or
       conversation history is reachable. **This decides threat T-06-03's strongest control** — a
       tool that reads the session-authenticated policy id itself does not have to trust a
       model-supplied parameter.
    D. **Egress — arbitrary host.** One `ces_requests` GET to a neutral public HTTPS endpoint that
       echoes the request and requires no credential. Record status code and whether a response
       body came back at all. Purpose: determine whether egress is allowlisted to
       `api.resend.com` or is open. **This single result gates three of the four fallbacks.**
    E. **Egress — Google APIs, unauthenticated.** One `ces_requests` GET each to
       `https://storage.googleapis.com/storage/v1/b?project=insurance-agent-demo-500614` and
       `https://firestore.googleapis.com/v1/projects/insurance-agent-demo-500614/databases`.
       A `401` or `403` is a **PASS for reachability** — it proves the host is reachable and only
       the credential is missing. A connection error is a FAIL.
    F. **Metadata server.** One `ces_requests` GET to
       `http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token`
       with header `Metadata-Flavor: Google`, and the same against `169.254.169.254`. Record the
       status code and, if 200, **the boolean `token_present` and the token length only — never the
       token itself, never any prefix of it.**
    G. **`ces_requests` kwarg surface.** Call the same harmless GET twice, once bare and once with
       `timeout=5`, and record whether the kwarg is accepted. This is the 05-07 defect, generalised
       — later plans must know which kwargs the shim tolerates before writing a tool that uses one.
    H. **Async execution.** Record the `executionType` values the API accepts on tool creation, by
       reading the created tool resource back. If an asynchronous execution type exists, note it —
       an async store write would remove the latency question from 06-04 entirely.

<threat_model>

| Boundary | Description |
|----------|-------------|
| CES tool sandbox → public internet | Tool source runs on Google infrastructure and can make outbound HTTPS. Whether that egress is allowlisted is the thing this plan measures. |
| CES tool sandbox → the claim store | The new boundary this phase creates. Whatever crosses it is a claim record containing synthetic PII. |
| Executor process → repo/transcript | Any secret read into the executor's process can leak into a file, a log or the transcript. |
