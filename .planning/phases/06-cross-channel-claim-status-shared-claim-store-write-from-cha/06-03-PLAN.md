<objective>
Close the write half of the loop on chat, and open the read half.

**Write:** when a chat claim resolves, it is persisted to the store — criterion 1.
**Read:** a chat customer who identifies themselves can hear the status of a claim filed elsewhere
— criterion 3's chat direction, proven here against the 06-02 fixtures so that this plan is not
blocked on 06-04, with the genuine cross-channel loop proven in 06-05.

how it does so is inherited from what has already gone wrong on this project — scripted anchored
replacement rather than inline retyping, the read agent kept separate from the write agent to halve
the blast radius, the full Phase 5 canary battery re-run, and a repoint gated in code on all of it.

Output: a new chat version live on `d7bfbb93`, and `06-03-CHAT-EVIDENCE.md`.

**Line endings.** The chat `claim_intake` instruction is pure **LF**; the voice one is **CRLF**
(176 CRLF + 7 bare LF). Anchor strings are therefore **not transferable between the two apps** —
derive every anchor by slicing it out of the chat app's own bytes at execution time. Never write
either instruction through a text file: a text-mode round-trip collapses `\r\n` and loses
characters, which then fails every length gate for reasons that look like server drift. Handle
instructions through JSON only.

   reads back byte-for-byte, **printing only lengths, booleans and short excerpts**.

   deployment is only ever repointed after the assertions pass.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Customer → chat agent | Untrusted. The customer supplies the policy id and may supply a claim reference; neither is proof of anything on its own. |
| Model → tool arguments | Untrusted. The model chooses what to pass to `lookup_claim`. |
| Chat agent → claim store | Synthetic claim records cross here on every resolution and every status inquiry. |
| Draft app → deployment `d7bfbb93` | The repoint is where an unproven build reaches customers. |
