<operational_rules>
1. **Bound every network call:** `curl --max-time 120 --connect-timeout 15`.
2. **Fresh `gcloud auth print-access-token` immediately before each conversation.** An expired token
   has stalled executors by hanging on an interactive reauth prompt.
3. **Write artifacts incrementally, one section per tool call.** Never compose a long document in a
   single tool-call argument — two executor sessions have died from an API transport error doing it.
4. **Never read, echo, print or persist `resolve_claim`'s source** on either app. It holds a live
   Resend key. If a secret is needed, use the 05-04 key-transplant: a single process reads the
   source, extracts the value into a variable, substitutes it into a `__PLACEHOLDER__` in the new
   tool body in memory, POSTs, then drops the variable. **The keyed source is never written to
   disk and the value is never printed** — the script emits `key_found: true` and a length, nothing
   more.
5. **No `importApp`.** Every on-disk export in this repo is STALE. Direct `apps.tools.create` /
   `apps.tools.patch` only, read-verify-patch-verify.
6. **No retry loops against CES.** A 429 is a stop. Conversation budget for this plan: **four**.
7. **No package-manager installs.** Standard library plus the platform-provided `ces_requests` only.
   A third-party dependency requirement is a blocking checkpoint, not an install.
8. **Client-level write gate.** Before every non-GET, assert the URL contains the intended app id
   and does **not** contain `9ae7a0c3`. Log refusals.
9. **`ces_requests` kwarg discipline.** Per 05-07, the platform's HTTP shim rejected `timeout=20`
   and the tool's own `except` branch hid it. Use only kwargs 06-01 probe G proved acceptable, and
   prove every tool by invocation.
</operational_rules>

    These are the behaviours the invocation tests in this task must demonstrate. Write the assertion

    `record_claim`:
    - Given a full set of claim fields, writes one record and returns `{"recorded": true,
      "claim_ref": ..., "status_code": 2xx}`.
    - Called twice with the same `claim_ref`, leaves exactly one record — the write is idempotent on
      claim reference, so a model that calls it twice cannot create a duplicate claim.
    - On a store error, returns `{"recorded": false, "status_code": ..., "error": ...}` and does not

      silent by design, every plan that changes this tool proves it by one live invocation.**
    - Makes exactly one outbound call per invocation. Never retries internally.

    `lookup_claim`:
    - Given a policy id with exactly one claim, returns `found: true`, the record's fields, and a
      Python-composed `status_line` carrying the claim reference, the device, the decision, the
      amount and the excess.
    - Given a policy id with several claims, returns the **most recent**, plus `match_count`, plus
      an `alternatives` list of compact descriptors (device + date), plus a `disambiguation_line`
      composed in Python that reads the most recent back and asks whether that is the one.
    - Given a policy id and a `selector` (a device word, a date, an ordinal like "the older one", or
      a claim reference), resolves it deterministically against that policy's claims and returns
      that record; on no match returns `found: false` with a composed `status_line` saying so.
    - Given a `claim_ref` that exists but belongs to a **different policy**, returns `found: false`
      — identical output to a reference that does not exist at all. It must not be possible to
      distinguish "someone else's claim" from "no such claim". This is threat T-06-03.
    - Given an unknown policy id or a policy with zero claims, returns `found: false` and a composed
      `status_line` saying there is nothing on file, **with no claim fields present in the response
      at all** — there must be nothing for a model to hallucinate from. This is criterion 5.
    - Normalises a spoken claim reference before matching: uppercase, strip spaces and punctuation,
      accept a missing `CLM` prefix, and map spelled-out digits to digits. Speech-to-text mangles
      alphanumerics, so `"C L M two four eight three two"` and `"clm 24832"` must both resolve.
    - **Never composes prose from the model's input.** Every string it returns is built in Python
      from stored fields and literal templates.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CES tool sandbox → claim store | Claim records containing synthetic customer name, policy id, device and figures cross here on every write and read. |
| Model → tool arguments | Untrusted: the model chooses what to pass. A model-supplied `policy_id` or `claim_ref` is an assertion, not an authentication. |
| Public internet → claim store | Anyone who learns the store's address may attempt a read. |
| Executor process → repo/transcript | Any secret read into the process can leak to a file, a log or the transcript. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Information disclosure | store shared secret held in tool source | mitigate | 05-04 key-transplant: single process, substituted in memory, never printed, never written to disk; the on-disk template keeps the `__PLACEHOLDER__`; grep gate for `re_…`/`ya29.`/`AKIA` at every task end |
| T-06-02 | Information disclosure | `resolve_claim` source (live Resend key) | mitigate | Never read into the transcript on either app; the transplant script emits only `key_found` and a length; `resolve_claim`'s whole-object hash asserted unchanged on both apps |
