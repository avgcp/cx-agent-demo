<objective>
**Claim status lookup on the PHONE — the beat that closes the loop.** A caller phones in, says who
they are and their policy number, and hears the real status of a claim they filed on chat: the same
reference, the same figures, spoken deterministically from the shared claim store.

Purpose: this is the moment the whole phase exists to produce. Everything before it built the store
and the tools; this plan puts the beat in front of a customer, on the channel where a mistake is
most expensive, and ships it to the live phone number.

**The design problem is criterion 4, not the lookup.** Speech-to-text mangles `CLM-24832`. A demo
that fails while the customer is still identifying themselves has failed before it starts. So the
caller is never asked to read a reference aloud — identification is by name and policy ID through
the `verify_identity` step voice already has and has already proven accepts spoken digits.

Output: a new voice version live on `d28bbcb0`, and `06-04-VOICE-EVIDENCE.md`.
</objective>

**Deployment schema.** There is no top-level `channelType` on a deployment resource. It is nested at
`deployment.channelProfile.channelType`. Asserting the flat path reads `None` and fails spuriously.

**Line endings.** The voice `claim_intake` and `claims_concierge` instructions are **CRLF**; chat's
are pure **LF**. Anchor strings are therefore **not transferable between the two apps** — derive
every anchor by slicing it out of the voice app's own bytes at execution time. Never round-trip
either instruction through a text file: a text-mode read collapses `\r\n` and silently loses
characters, which then fails every length and hash gate for reasons that look like server drift.
Handle instructions through JSON only.
</environment>

<operational_rules>
Each of these has already cost this project a session or a defective deployment.

1. **Bound every network call:** `curl --max-time 120 --connect-timeout 15`. No unbounded call.
2. **Fresh `gcloud auth print-access-token` immediately before each conversation.** An expired token
   has stalled executors on an interactive reauth prompt.
3. **Write artifacts incrementally, one section per tool call.** Never compose a long document in a
   single tool-call argument — two executor sessions have died from an API transport error doing it.
4. **Never read, echo, print or persist `resolve_claim`'s source** on either app. It holds a live
   Resend key. This plan has no reason to touch it and asserts it byte-unchanged.
5. **No `importApp`, ever.** It silently deletes server-only tools, and every on-disk export in this
   repo is STALE. Direct `apps.agents.patch` / `apps.tools.patch` only, read-verify-patch-verify.
6. **Edit instructions by scripted `str.replace()` only, never by retyping inline.** The technique
   that works: a script that GETs the agent, replaces one small region, asserts the anchor is
   unique, asserts a pre-stated delta bound, PATCHes, and reads back byte-for-byte — **printing only
   lengths, booleans and short excerpts.** Editing `claim_intake` inline has killed agents on this
   project; `claims_concierge` gets the same discipline.
7. **No retry loops against CES.** Quota is ~1,000 input tokens/min against a 120–150k-token
   conversation. **Conversation budget for this plan: six.** A 429 is a stop. One spaced retry
   (≥90 s) of a **single turn** is permitted; a loop is not.
8. **Client-level write gate.** Before every non-GET, assert the URL names `6e01e4a5` (or
   `a2f621e4` only in Task 1's named parity fallback) and does **not** name `9ae7a0c3`. Log refusals.
9. **Every conversation runs against the DRAFT** (`runSession` with **no** `config.deployment`),
   except the single explicitly-labelled LIVE control run in Task 2. The deployment is repointed
   only after the assertions pass.
10. **No package-manager installs.** Standard library plus the platform-provided `ces_requests` only.
    A third-party dependency requirement is a blocking checkpoint, not an install.
11. **`ces_requests` kwarg discipline.** 05-07's most expensive defect was `timeout=20` passed to
    `ces_requests.post` — the shim rejected it, the tool's own `except` swallowed it, and the mailer
    had never delivered a single email. **A tool that swallows its own exceptions cannot be verified
    by reading it.** If Task 1's fallback patches `lookup_claim`, it is re-proven by invocation.
</operational_rules>
