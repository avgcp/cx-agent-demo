<objective>
Ship Spanish on the chat app: a customer can complete a full claim in Spanish, and every
customer-facing string is genuinely Spanish rather than English text wearing a Spanish voice.

Purpose: this is success criterion 5, and 05-RESEARCH.md is emphatic that it is a **content**
problem wearing a config costume. `languageSettings` is already written by 05-03 and does nothing
for the strings this build spent five days making deterministic. `resolve_claim`'s `explanation`
is a hardcoded Python template; the platform will not translate it, and letting the model
translate it would reopen exactly the class of defect that v7→v9 was spent closing. Spanish must
be a **second deterministic string**, selected in code, not a model translation of the first.

Output: bilingual deterministic tools, a language directive on `claim_intake`, a cut version
serving on `d7bfbb93` — or the pre-plan version still serving and a recorded failure.
</objective>

<hard_constraints>
These apply to every task and are not negotiable.

1. **Determinism is not negotiable.** The claim amount comes from the tariff and never from the
   model, in either language. The spoken Spanish decision must be byte-identical to the Spanish
   string `resolve_claim` computes, exactly as the English one already is. Spanish is a **second
   template**, never a translation performed at runtime.

2. **The Resend API key must never enter the transcript, a scratchpad file, or the repo.**
   `resolve_claim` and `send_claim_email` hold a live key. This plan has to edit `resolve_claim`
   anyway, so the rule is mechanical, not aspirational:
   - The tool source is fetched **into memory inside a single script** and never written whole to
     disk and never printed whole.
   - Any slice of source the executor is allowed to read is produced by the **extraction gate**
     defined in Task 1 and must pass its redaction assertions first.
   - Every script ends with a gate asserting that nothing it printed, and no file it wrote,
     matches `\bre_[A-Za-z0-9_]{16,}` or contains the substrings `RESEND`, `API_KEY`, `SECRET`,
     `Bearer ` (case-insensitive) outside of this plan's own quoted names.
   - Tool listings are filtered by `displayName` in-script; never print a tool list whole.

3. **Never `importApp`.** Use `apps.tools.patch` / `apps.agents.patch` / `apps.patch` with an
   `updateMask`, read-verify-patch-verify. **Every exported package on disk is STALE** — do not
   read or reuse any zip in any scratchpad.

4. **Large instructions are edited only by scripted `str.replace()` against the API.** Write the
   replacement block to a file by heredoc; the script GETs, asserts anchor uniqueness, replaces
   exactly one contiguous region, asserts content and a bounded length delta, PATCHes, reads back
   byte-for-byte. Print only lengths, booleans and short excerpts. **Never compose the 18,496-char
   instruction inline in tool-call arguments** — three executor sessions have died doing that.

5. **Write only to `a2f621e4`.** Gate every mutating URL on that literal in-script and explicitly
   refuse `6e01e4a5` and `9ae7a0c3` for any non-GET.

6. **Live runs go against the DRAFT app** — `runSession` with no `config.deployment`, proven
   accepted in `260810-k5x`. The demo rig is never exposed to an unverified build.

7. **The repoint is conditional and reversible.** `d7bfbb93` stays on the pinned rollback version
   until every assertion in Task 3 passes. If any fails, do not repoint; record the failure.

8. **CES quota is the binding constraint.** ~120–150k input tokens per conversation against a
   1,000/min `RunSession LLM tokens` limit. This plan is budgeted at **two conversations, six
   turns total** — one English canary, one Spanish claim. Pace turns ≥55 s apart. **No retry
   loops** — at most one spaced retry of a single quota-failed turn.

9. **Mock data only.** Every figure, policy and name comes from the existing seeded records
   (PDP100294 / Jordan Rivera). The Spanish strings introduce no new field, no new figure and no
   new fact — they are translations of what already ships.
</hard_constraints>

  <action>
Add a second deterministic language to every TOOL-owned string, using the same edit discipline that
survived the three sessions that died: one script, source in memory only, replacement text loaded
from a file, output limited to lengths and booleans.

**The mechanism, decided.** `preferred_language` is an **explicit input parameter** on each
TOOL-owned tool, not a session variable. 05-RESEARCH.md recommends a session variable, and this
plan deviates deliberately: nothing in this app currently writes a session variable from an
instruction (variables are written by tools, per `verify_identity` writing `uninsured_device`), so
a session variable would need a writer that does not exist, and adding one would change
`variableDeclarations` while 05-04's packet work is landing on the same app. A parameter is
deterministic per call, observable in the conversation record, and touches nothing else. Record
this deviation in the summary.

**Normalisation is in code, not in the prompt.** The tool computes `lang = "es" if
str(preferred_language).strip().lower().startswith("es") else "en"`. Any unexpected value —
`None`, `es-US`, `Spanish`, empty, a typo — resolves to a valid key. There is no path to a
`KeyError` on stage. This is the control 05-RESEARCH.md's Security Domain section asks for.

**Step A — declare the parameter.** For each TOOL-owned tool, `PATCH` its declared `parameters` to
add `preferred_language` as an optional `STRING`, described as: the language the customer is using
in this conversation — `es` if they have been writing in Spanish, otherwise `en`. Read the schema
back with `retrieveToolSchema` and assert the new parameter is present **and** that every
pre-existing parameter is byte-identical to what it was. `updateMask` must name only the fields
being changed; a broad mask replaces whole objects and is how the visually-verified card was nearly
destroyed in `260810-k5x`.

**Step B — insert the template dicts.** Write the Spanish template block to a scratchpad file by
heredoc — it contains no secret, so it may be authored inline. Then run one script that: GETs the
tool source into memory; asserts the anchor region located in Task 1 Step C is still present and
occurs **exactly once**; performs a single `str.replace()` that turns each English literal into a
two-key dict keyed `en`/`es` and routes each return through `lang`; asserts a bounded length delta
consistent with the authored Spanish (state the bound explicitly before running, and fail outside
it); PATCHes with `updateMask` naming only the code field; reads back and asserts byte-for-byte
equality with what was sent. Print only: the before length, the after length, the delta, the
anchor-uniqueness boolean, and the read-back-equal boolean. **Never print the source.**

**Step C — assert the English path is untouched, structurally.** In the same script, before
PATCHing, assert that every English literal enumerated in Task 1 Step D still appears in the new
source **exactly as many times as before**, and that the count of `return` keys is unchanged.
Additionally assert the following are still present and unchanged, by count: the tariff table, the
on-the-spot cutoff value, the excess value, the `CLM-` reference construction, the
`card_product_item` assembly including `price.units` as an `int`, and the `photo_blocked` branch's
refusal to name a payout figure. A change in any of these counts is a regression and must abort the
patch. These are structural counts on in-memory strings — they are printed as integers, never as
the strings themselves.

**Step D — the same treatment for `send_claim_email`, only if Task 1 said TOOL.** If Task 1
